= osgi-otel: OpenTelemetry Java Agent Extension for OSGi
:toc:
:toc-placement: preamble
:icons: font
:source-highlighter: rouge
:otel-agent-version: 2.32.0

OpenTelemetry Java Agent extension that emits spans for OSGi inter-bundle data flow, Eclipse UI actions, and - optionally - rule-based application layer spans.
It instruments `BundleContext.getService(ServiceReference)` (tagging caller bundle, provider bundle, and service interface) and Eclipse command/JFace-action execution, so a user gesture becomes a span that the downstream service, HTTP, and DB work nests under.
With `otel.app.span.rules` it additionally instruments any set of your application's classes, so plain controller-to-service calls that bypass the OSGi service registry become spans in the same trace.

The driving use-case is observing data flow in Eclipse RCP applications (Mylyn, Equinox-based products).
The OSGi instrumentation is plain OSGi; the Eclipse UI instrumentation is a separate module that self-disables when the Eclipse classes are absent.

== Status

Very early v1.

* `BundleContext.getService` instrumented (OSGi service lookups)
* Eclipse UI actions instrumented: Commands framework (`Command.executeWithChecks`) and JFace `IAction.run`
* Rule-based application layer spans (opt-in `app-span` module, `otel.app.span.rules`)
* File-based JSON-Lines exporter (no Jaeger/OTLP back end required)
* Optional bundle-name regex filter (cross-bundle-only / include / exclude)
* Embedded-Equinox integration test, runs in CI

== What gets instrumented

[cols="1,2,2"]
|===
|Module |Chokepoint |Span name + attributes

|`osgi-bundle-context`
|`BundleContext.getService(ServiceReference)`
|`BundleContext.getService <service>`; `osgi.caller.bundle`, `osgi.provider.bundle`, `osgi.service.class`

|`eclipse-ui` (commands)
|`org.eclipse.core.commands.Command.executeWithChecks`
|`command <name>`; `eclipse.command.id`, `eclipse.command.name`, plus business context (see below)

|`eclipse-ui` (actions)
|`org.eclipse.jface.action.IAction.run()` / `runWithEvent()`
|`action <text>`; `eclipse.action.id`, `eclipse.action.text`, `eclipse.action.class`, plus business context (see below)

|`app-span` (opt-in, rule-based)
|Any method whose declaring class matches an `otel.app.span.rules` entry (base class or FQCN regex)
|`<rule> <RuntimeClass>.<method>`; `app.span.rule`, `code.function`, `code.namespace`, `osgi.provider.bundle`, `osgi.caller.bundle`
|===

The `eclipse-ui` module opens a span for each user gesture and makes it current for the duration of the handler/action.
Same-thread downstream spans - service lookups, HTTP, and JDBC/Hibernate from the agent's own built-in instrumentations - therefore nest under it into one coherent trace.
It self-disables when the Eclipse classes are absent; force either module off with `-Dotel.instrumentation.eclipse-ui.enabled=false` (or `...osgi-bundle-context.enabled=false`).

==== Business context on UI spans

Each command/action span is enriched, best-effort, with _what the user was acting on_.
These attributes are only present when they can be resolved, so downstream `jq`/Jaeger queries must tolerate their absence.

`eclipse.trigger.widget.class`:: The runtime class of the SWT widget that fired the gesture (button, menu item, tree, text field, ...).
`eclipse.selection.class`:: The class of the current workbench selection - for a structured selection, the class of its first element, i.e. your *domain object*.
Command spans only.
`eclipse.selection.size`:: Number of selected elements (structured selections only).
`eclipse.selection.label`:: The first selected element's label (its `toString()`) - the domain object's *value*, command spans only.
This is domain data (PII), so it is *opt-in*: enable with `-Dosgi.capture.selection.label=true` and cap the length with `-Dosgi.capture.selection.label.max=N` (default 64).
`eclipse.trigger.widget.text`:: The text/label/entered value of the triggering widget.
This can contain user input (PII), so it is *opt-in*: enable with `-Dosgi.capture.widget.text=true` and cap the recorded length with `-Dosgi.capture.widget.text.max=N` (default 64).

SWT and the JFace selection APIs are read reflectively, because they are intentionally off the compile classpath; a host without them simply yields empty attributes rather than an error.

NOTE: Async flows (Jobs, `Display.asyncExec`, EventAdmin) do not yet propagate context across the thread hop - see the roadmap.

[#app-span-rules]
=== Application layer spans: rule-based instrumentation (opt-in)

Many OSGi applications resolve their internal dependencies without the OSGi service registry - a controller class in one bundle calls a plain service class in another.
The `osgi-bundle-context` module sees none of those calls, so the layer-to-layer data flow stays invisible in the trace.

The `app-span` module closes this gap without touching the application code: you declare span *rules* that name the classes to instrument, and every call of a matching class's methods becomes a span that downstream `BundleContext.getService`, HTTP, and JDBC/Hibernate spans nest under.

[cols="1,3",opts="header"]
|===
|Property |Meaning

|`otel.app.span.rules`
|Comma-separated `prefix:matcher` entries; the module is enabled only when at least one rule is set.
A matcher without any of the regex metacharacters `* + ? ( ) [ ] { } | ^` is a *base class*: the rule matches that class and all of its subtypes (dots and `$` are legal in class names and are not metacharacters).
Any other matcher is a Java regex searched (`find()`) in the fully qualified class name.
The first matching rule wins.

|`otel.app.span.exclude-methods`
|Java regex (full match, default `^(toString|hashCode|equals|getClass)$`).
Matching methods are not instrumented at all.

|`otel.instrumentation.app-span.enabled`
|Standard OTel switch; `false` disables the module even when rules are set.
|===

Each span is named `<prefix> <RuntimeClass>.<method>` (the *runtime* class of the receiver, so an overridden method shows the concrete implementation) and carries:

`app.span.rule`:: The matching rule's prefix.
`code.function`:: The fully qualified declaring class plus the method name.
`code.namespace`:: The declaring class's package.
`osgi.provider.bundle`:: The bundle providing the instrumented class (the classloader's bundle, when it is an OSGi wiring).
`osgi.caller.bundle`:: The bundle of the direct caller, resolved best-effort from the stack (the first caller frame whose class is loadable in the instrumented class's classloader); `unknown` when unresolvable - e.g. reflective calls, or a caller in a bundle the instrumented bundle does not see.

Example (generic; adapt the class names to your application):

[source,bash]
----
# Span every method of MyServiceBase and all its implementations as "service ...",
# and every class in the controller packages as "controller ..."
-Dotel.app.span.rules=service:com.example.app.service.MyServiceBase,controller:^com\.example\.app\.controller\..*

# Drop getter/setter noise on top of the default exclusions
-Dotel.app.span.exclude-methods='^(toString|hashCode|equals|getClass|(get|set|is)[A-Z].*)$'
----

NOTE: The rules are read once at agent load time, so a JVM restart is required to change them.

=== Diagnostic: Event-cascade tracing (opt-in)

A third, *opt-in* module `eclipse-events` turns each fired model event into a nested span, so an event cascade shows up as a tree: depth is the cascade depth, span count is how many events one gesture triggers, and durations show the time cost.
It instruments the two central fan-out points - EMF `BasicNotifierImpl.eNotify` and JavaBeans `PropertyChangeSupport.firePropertyChange` (the latter is a JDK class and may not be instrumentable in every host).

It is a firehose, so it is *disabled by default*.
Enable it only while investigating:

[source,bash]
----
-Dotel.instrumentation.eclipse-events.enabled=true
----

Attributes: `eclipse.event.kind`, `eclipse.event.source`, `eclipse.event.type` (EMF), `eclipse.event.property` and `eclipse.event.listeners` (fan-out width, JavaBeans).
The EMF hook deliberately avoids reading the changed feature's name, because touching the EMF metamodel from inside `eNotify` can re-enter `EcorePackage` during its own class initialization and crash the host.
The `samples/` scripts expose it as `OSGI_OTEL_TRACE_EVENTS=true`.

CAUTION: Per-event span creation adds overhead that inflates the measured durations - use this for depth, count, and relative hotspots, not for precise wall-clock timing.

=== Diagnostic: Transaction trigger stack (opt-in)

Hibernate `Transaction.commit` spans often appear as *orphan roots* with no visible cause, because the gesture that triggered them ran on another thread - an Eclipse `Job`, `Display.asyncExec`, an auto-save - across which the trace context is not yet propagated.

The *opt-in* module `hibernate-stack` records the call stack at `org.hibernate.Transaction.begin` and `commit` and emits it as a span.
The stack is thread-local, so it reveals the caller chain even when the trace link was lost: `begin` shows who opened the unit of work, `commit` shows who forced the write.

[source,bash]
----
-Dotel.instrumentation.hibernate-stack.enabled=true
----

Each fired transaction then produces a `hibernate.tx.begin` / `hibernate.tx.commit` span with `code.function` and `code.stacktrace` (the caller chain, one `at ...` frame per line).
Cap the recorded depth with `-Dosgi.capture.stack.max=N` (default 32).
The `samples/` scripts expose it as `OSGI_OTEL_TRACE_TX_STACK=true`.

NOTE: The module needs no Hibernate dependency and touches no Hibernate type - it matches `org.hibernate.Transaction` by name only, so hosts without Hibernate are simply never matched.

== Quick start

. Build everything and assemble `dist/` (agent + both extension JARs):
+
[source,bash,subs="attributes+"]
----
./mvnw -B install -DskipTests
./mvnw -B dependency:copy \
  -Dartifact=io.opentelemetry.javaagent:opentelemetry-javaagent:{otel-agent-version} \
  -DoutputDirectory=dist -Dmdep.stripVersion=true
cp osgi-otel-extension/target/osgi-otel-extension-0.1.0-SNAPSHOT.jar dist/
cp osgi-otel-file-exporter/target/osgi-otel-file-exporter-0.1.0-SNAPSHOT.jar dist/
----

. Attach the agent to your application.
See <<Installing into your own OSGi application>> for the generic recipe, or copy a ready-made launcher from `samples/` (see <<Samples>>).
The default `file` exporter writes one JSON object per span to `traces.jsonl`.

. Inspect the file:
+
[source,bash]
----
wc -l traces.jsonl
jq -r '.attributes["osgi.service.class"]' traces.jsonl | sort | uniq -c | sort -rn | head
----

== Configuration

The extension and the file exporter are configured entirely through JVM system properties (`-D...`).
Nothing is mandatory beyond what every OpenTelemetry agent needs (`-javaagent` and `-Dotel.javaagent.extensions`); every property below has a default.

[cols="2,1,3"]
|===
|System property |Default |Purpose

|`otel.service.name`
|`unknown_service:java`
|Logical name of the *whole application* (the standard OTel `service.name` resource attribute; what Jaeger groups traces by).
Not to be confused with an OSGi _service_ - those appear per span in `osgi.service.class`.

|`otel.traces.exporter`
|`otlp` (agent default)
|Set to `file` for the bundled JSON-Lines exporter; also `otlp`, `logging-otlp`, `logging`.

|`otel.exporter.file.path`
|`traces.jsonl`
|Output file for `otel.traces.exporter=file` (resolved against the working directory).

|`otel.exporter.file.append`
|`true`
|`false` truncates the file on each start.

|`otel.exporter.otlp.endpoint`
|agent default
|OTLP collector endpoint; use the HTTP port (e.g. `http://localhost:4318`) for `otel.traces.exporter=otlp`.

|`osgi.capture.widget.text`
|`false`
|`true` records the triggering widget's text/entered value on `eclipse-ui` spans (`eclipse.trigger.widget.text`).
May contain user input (PII) - opt-in.

|`osgi.capture.widget.text.max`
|`64`
|Maximum number of characters of widget text to record; longer values are truncated.

|`osgi.capture.selection.label`
|`false`
|`true` records the first selected element's label on command spans (`eclipse.selection.label`, the element's `toString`).
Domain data (PII) - opt-in.

|`osgi.capture.selection.label.max`
|`64`
|Maximum number of characters of the selection label to record; longer values are truncated.

|`osgi.capture.stack.max`
|`32`
|Maximum number of stack frames recorded by the `hibernate-stack` diagnostic in `code.stacktrace`.

|`otel.app.span.rules`
|unset
|The `app-span` module's span rules: comma-separated `prefix:matcher` entries where the matcher is a base class or a class-name regex.
The module is enabled only when set (see <<app-span-rules>>).

|`otel.app.span.exclude-methods`
|`^(toString|hashCode|equals|getClass)$`
|`app-span`: method-name regex (full match) of methods to leave uninstrumented.

|`osgi.filter.cross-bundle-only`
|`false`
|`true` drops spans where caller and provider are the same bundle.

|`osgi.filter.bundle.include`
|unset
|Java regex.
Span emitted only if caller OR provider matches.

|`osgi.filter.bundle.exclude`
|unset
|Java regex.
Span dropped only if caller AND provider both match.
|===

NOTE: The `osgi.filter.*` and `otel.app.span.*` properties are read once at extension load time, so a JVM restart is required to change them.

The launcher scripts under `samples/` wrap these properties behind convenience `OSGI_OTEL_*` environment variables (all optional) - see `samples/README.adoc`.

== Bundle filter examples

These are the system properties; the `samples/` scripts expose the same behaviour via `OSGI_OTEL_FILTER_*` environment variables.
Replace `com.example` with your application's bundle-symbolic-name prefix.

[source,bash]
----
# Only cross-bundle calls (the typical "I want to see data flow" filter)
-Dosgi.filter.cross-bundle-only=true

# Anything involving your own bundles (caller or provider matches)
-Dosgi.filter.bundle.include='^com\.example\..*'

# Drop pure Equinox-internal noise; keep osgi-to-userbundle calls
-Dosgi.filter.bundle.exclude='^org\.eclipse\.osgi$'

# Combine: only your-bundle-involved cross-bundle calls
-Dosgi.filter.cross-bundle-only=true -Dosgi.filter.bundle.include='^com\.example\..*'
----

The filter is applied _before_ the span is created, so excluded calls cost essentially nothing.

== Exporter modes

file:: Default of the bundled exporter.
Writes OTLP-shaped JSON (one object per line) to `otel.exporter.file.path`.
No back end required, easy to grep/jq, suitable for offline analysis.

otlp:: Sends via OTLP HTTP to a Jaeger or other OTLP collector.
Start Jaeger first:
+
[source,bash]
----
docker run -d --rm --name jaeger \
  -p 16686:16686 -p 4317:4317 -p 4318:4318 \
  jaegertracing/all-in-one:latest
----
+
UI at http://localhost:16686; look for your `otel.service.name`.

logging-otlp:: OpenTelemetry's built-in OTLP-JSON-to-stdout exporter.
Useful if you want to pipe everything yourself, but the output is mixed with the application's own logs.

logging:: Same as `logging-otlp` but with a human-readable text format.

== Installing into your own OSGi application

This is the generic recipe.
The scripts under `samples/` are just convenience wrappers around exactly these steps (see <<Samples>>).

Tracing is attached at JVM start via the OpenTelemetry Java Agent - there is nothing to install _inside_ your OSGi framework, no bundle to deploy, and no code change.
You need three JAR files on disk and a handful of `-D` system properties.

NOTE: Everything here runs on *Java 8 or newer*.
The OpenTelemetry Java Agent 2.x supports a Java 8+ runtime; this extension is compiled to Java 8 bytecode.

=== Step 1: Obtain the three JARs

[cols="2,1,3"]
|===
|Artifact |From |Role

|`io.opentelemetry.javaagent:opentelemetry-javaagent:{otel-agent-version}`
|Maven Central
|The agent itself (the `-javaagent`).

|`net.aschemann.otel:osgi-otel-extension:0.1.0-SNAPSHOT`
|GitHub Packages
|The OSGi instrumentation.

|`net.aschemann.otel:osgi-otel-file-exporter:0.1.0-SNAPSHOT`
|GitHub Packages
|The JSON-Lines file exporter.
|===

You do *not* need to clone this repository to consume the packages.

GitHub Packages, however, requires authentication even for reads of public Maven packages.
You authenticate as *yourself*: any GitHub account with a personal access token works - it does *not* have to be the package owner, and no shared/maintainer credentials are involved.
Configure your own token *once* in your personal `~/.m2/settings.xml` (not the `settings.xml` in this repo, which only serves the maintainer's deploy):

[source,xml]
----
<!-- ~/.m2/settings.xml -->
<settings>
  <servers>
    <server>
      <!-- id must match the repository id on the command line below -->
      <id>github-osgi-otel</id>
      <username>your-github-user</username>
      <!-- personal access token with the read:packages scope -->
      <password>ghp_...</password>
    </server>
  </servers>
</settings>
----

Then download the three JARs - no `-s`, no repo checkout:

[source,bash,subs="attributes+"]
----
mkdir -p otel-libs

# The agent comes from Maven Central (no auth needed)
mvn dependency:copy -Dmdep.stripVersion=true -DoutputDirectory=otel-libs \#<1>
  -Dartifact=io.opentelemetry.javaagent:opentelemetry-javaagent:{otel-agent-version}

# The two extensions come from GitHub Packages (repo id = server id above)
mvn dependency:copy -Dmdep.stripVersion=true -DoutputDirectory=otel-libs \#<2>
  -DremoteRepositories=github-osgi-otel::::https://maven.pkg.github.com/ascheman/osgi-otel \
  -Dartifact=net.aschemann.otel:osgi-otel-extension:0.1.0-SNAPSHOT
mvn dependency:copy -Dmdep.stripVersion=true -DoutputDirectory=otel-libs \#<3>
  -DremoteRepositories=github-osgi-otel::::https://maven.pkg.github.com/ascheman/osgi-otel \
  -Dartifact=net.aschemann.otel:osgi-otel-file-exporter:0.1.0-SNAPSHOT
----
<1> Downloads `opentelemetry-javaagent.jar`.
<2> Downloads `osgi-otel-extension.jar`.
<3> Downloads `osgi-otel-file-exporter.jar`.

TIP: If you built this project yourself (`mvn -B install`), the two extension JARs are already in your local `~/.m2` and you can drop the `-DremoteRepositories=...` argument entirely.

==== Alternative: Download with curl (no Maven)

GitHub Packages is a plain Maven-layout HTTPS repo, so `curl` works too (same token, Basic auth).
The agent comes from Maven Central without a token:

[source,bash,subs="attributes+"]
----
curl -L -o otel-libs/opentelemetry-javaagent.jar \
  https://repo1.maven.org/maven2/io/opentelemetry/javaagent/opentelemetry-javaagent/{otel-agent-version}/opentelemetry-javaagent-{otel-agent-version}.jar
----

For a released (non-snapshot) version the address is deterministic:

[source,bash]
----
curl -Lfu "$GITHUB_LOGIN:$GITHUB_TOKEN" -o otel-libs/osgi-otel-extension.jar \
  https://maven.pkg.github.com/ascheman/osgi-otel/net/aschemann/otel/osgi-otel-extension/0.1.0/osgi-otel-extension-0.1.0.jar
----

For a `-SNAPSHOT` the real filename is timestamped, so read it from `maven-metadata.xml` first:

[source,bash]
----
BASE=https://maven.pkg.github.com/ascheman/osgi-otel/net/aschemann/otel/osgi-otel-extension/0.1.0-SNAPSHOT
VER=$(curl -sfu "$GITHUB_LOGIN:$GITHUB_TOKEN" "$BASE/maven-metadata.xml" \
        | grep -oE '<value>[^<]+</value>' | tail -1 | sed -E 's/<[^>]+>//g')
curl -Lfu "$GITHUB_LOGIN:$GITHUB_TOKEN" -o otel-libs/osgi-otel-extension.jar \
  "$BASE/osgi-otel-extension-${VER}.jar"
----

For snapshots `mvn dependency:copy` is simpler (it resolves the timestamp itself); for a fixed release `curl` is a lighter option.

NOTE: GitHub Packages never allows anonymous Maven reads (only its Container registry does); for token-free consumption later, mirror the artifacts to Maven Central or a service like JitPack.

=== Step 2: Decide where the JARs live

The directory does not matter - the agent loads them by absolute (or launcher-relative) path.
Any location the JVM process can read works: a sibling `otel-libs/` folder, `dropins/`, or a fixed system path.
The extensions are *not* OSGi bundles from the framework's point of view; they live entirely inside the agent's isolated class loader.

=== Step 3: Add the JVM system properties

Append these to the JVM command line (adjust the three paths):

[source,bash]
----
-javaagent:/path/to/otel-libs/opentelemetry-javaagent.jar
-Dotel.javaagent.extensions=/path/to/otel-libs/osgi-otel-extension.jar,/path/to/otel-libs/osgi-otel-file-exporter.jar
-Dotel.service.name=my-osgi-app
-Dotel.traces.exporter=file
-Dotel.exporter.file.path=/path/to/traces.jsonl
-Dotel.exporter.file.append=true
-Dotel.metrics.exporter=none
-Dotel.logs.exporter=none
----

Both extension JARs are passed to `-Dotel.javaagent.extensions` as a single comma-separated value.
Disabling the metrics and logs exporters keeps the agent from complaining about missing OTLP endpoints.

=== Step 3 (variant): Where exactly to put them per launcher

Plain `java` launcher::
Put the arguments on the command line (or in `JAVA_TOOL_OPTIONS` / `JAVA_OPTS`) *before* `-jar` / the main class.

Bare Equinox (`java -jar org.eclipse.osgi.jar`)::
Same - the `-javaagent` and `-D...` arguments go before `-jar`.

Eclipse / Equinox product (`eclipse.ini`)::
Append them *after* the `-vmargs` line (which must be the last section of the file); everything below `-vmargs` is handed to the JVM verbatim.

=== Step 4 (optional): Send to Jaeger instead of a file

Swap the three `file` exporter properties for OTLP and start a collector:

[source,bash]
----
docker run -d --rm --name jaeger \#<1>
  -p 16686:16686 -p 4317:4317 -p 4318:4318 \
  jaegertracing/all-in-one:latest
----
<1> Jaeger UI at http://localhost:16686.

[source,bash]
----
-Dotel.traces.exporter=otlp
-Dotel.exporter.otlp.endpoint=http://localhost:4318
----

=== Step 5 (optional): Reduce noise with bundle filters

The same filter system properties work here directly (replace `com.example` with your bundle prefix):

[source,bash]
----
-Dosgi.filter.cross-bundle-only=true
-Dosgi.filter.bundle.include=^com\.example\..*
-Dosgi.filter.bundle.exclude=^org\.eclipse\.osgi$
----

See <<Bundle filter examples>> for what each one does.

== Analyzing traces with jq

All examples assume `traces.jsonl` in the current directory.

=== Top-N most-queried services

[source,bash]
----
jq -r '.attributes["osgi.service.class"] // "n/a"' traces.jsonl \
  | sort | uniq -c | sort -rn | head -20
----

=== Top callers and providers

[source,bash]
----
echo "Top callers:"
jq -r '.attributes["osgi.caller.bundle"] // "n/a"' traces.jsonl \
  | sort | uniq -c | sort -rn | head

echo "Top providers:"
jq -r '.attributes["osgi.provider.bundle"] // "n/a"' traces.jsonl \
  | sort | uniq -c | sort -rn | head
----

=== Cross-bundle calls only (post-hoc filter)

[source,bash]
----
jq -c 'select(.attributes["osgi.caller.bundle"]
            != .attributes["osgi.provider.bundle"])
       | {caller:   .attributes["osgi.caller.bundle"],
          provider: .attributes["osgi.provider.bundle"],
          service:  .attributes["osgi.service.class"]}' traces.jsonl \
  | sort -u
----

=== Edge list for a Mermaid/Graphviz diagram

[source,bash]
----
jq -r 'select(.attributes["osgi.caller.bundle"]
            != .attributes["osgi.provider.bundle"])
       | "\(.attributes["osgi.caller.bundle"]) -> \(.attributes["osgi.provider.bundle"])"' \
  traces.jsonl | sort -u
----

Pipe this into Graphviz directly:

[source,bash]
----
{
  echo 'digraph osgi { rankdir=LR;'
  jq -r 'select(.attributes["osgi.caller.bundle"]
              != .attributes["osgi.provider.bundle"])
         | "\"\(.attributes["osgi.caller.bundle"])\" -> \"\(.attributes["osgi.provider.bundle"])\";"' \
    traces.jsonl | sort -u
  echo '}'
} | dot -Tsvg > bundle-graph.svg
----

=== Service-class fan-in (which bundles consume a given service?)

[source,bash]
----
SERVICE='org.osgi.service.event.EventHandler'
jq -r --arg s "$SERVICE" \
  'select(.attributes["osgi.service.class"] == $s)
   | .attributes["osgi.caller.bundle"]' traces.jsonl \
  | sort | uniq -c | sort -rn
----

=== All spans involving a specific bundle (as caller or provider)

[source,bash]
----
BUNDLE='com.example.myapp.core'
jq -c --arg b "$BUNDLE" \
  'select(.attributes["osgi.caller.bundle"]   == $b
       or .attributes["osgi.provider.bundle"] == $b)' traces.jsonl
----

=== Span timing summary (microseconds)

[source,bash]
----
jq -r '"\((.end_unix_nano - .start_unix_nano) / 1000)\t\(.name)"' traces.jsonl \
  | sort -rn | head -20
----

=== Quick sanity check of the file

[source,bash]
----
echo "Total spans:    $(wc -l < traces.jsonl)"
echo "Distinct trace IDs: $(jq -r .trace_id traces.jsonl | sort -u | wc -l)"
echo "Distinct services:  $(jq -r '.attributes["osgi.service.class"] // empty' traces.jsonl | sort -u | wc -l)"
----

== Building and testing

[source,bash]
----
mvn -B verify
----

Runs unit tests (none yet) and the integration tests in `osgi-otel-it`.
They start an embedded Equinox 3.15.300 with the OpenTelemetry `agent-for-testing` attached, install the test bundle, and assert on the captured spans: `BundleContextGetServiceIT` for the `BundleContext.getService` span, `AppSpanIT` for the rule-based `app-span` spans (nested controller/service spans, excluded methods absent).

== Deployment

This is for the *maintainer* (or CI); consumers only download, see <<Installing into your own OSGi application>>.

The parent POM declares a `github` profile for publishing snapshot artifacts to GitHub Packages.
The profile activates automatically when `GITHUB_TOKEN` is set.
The repo's own `settings.xml` supplies the `github` server credentials from the same environment variables:

[source,bash]
----
export GITHUB_LOGIN=ascheman
export GITHUB_TOKEN=...            # PAT with write:packages
mvn -B -s settings.xml deploy
----

All four modules publish to `https://maven.pkg.github.com/ascheman/osgi-otel`.
In CI the deploy step regenerates `settings.xml` via `setup-java`, so it uses the workflow's `GITHUB_TOKEN` instead.

== Implemented so far

* *OSGi service flow* - `BundleContext.getService` spans tagged with caller/provider bundle and service interface, with a load-time bundle filter.
* *Rule-based application spans* - `app-span` module (opt-in): spans for any class matched by `otel.app.span.rules` (base class or FQCN regex), to make layer boundaries (controller -> service -> DB) visible in one trace without touching the application code.
* *Eclipse UI gestures* - `eclipse-ui` module: spans for `Command.executeWithChecks` and JFace `IAction.run`/`runWithEvent`, enriched with business context (triggering widget class, workbench selection class/size; opt-in widget text and selection label).
* *Event-cascade diagnostic* - `eclipse-events` module (opt-in): EMF `eNotify` + JavaBeans `firePropertyChange` as nested spans, to measure cascade depth, width and timing.
* *Transaction trigger stack* - `hibernate-stack` module (opt-in): call stack at `org.hibernate.Transaction.begin`/`commit`, to reveal what triggered an orphan transaction.
* *File exporter* - JSON-Lines `SpanExporter` for offline `jq`/Graphviz analysis, plus GitHub Packages deployment of all modules.

== Roadmap

Instrumentation targets::

. *Producer / consumer / relay test bundles*, to make the IT show real bundle-to-bundle hops, not just system-bundle to user-bundle.
. *Async context propagation across Eclipse `Job`s and `Display.asyncExec`*, so work scheduled off the UI thread nests under the originating gesture instead of surfacing as an orphan root (the gap behind orphan `Transaction.commit` spans; the agent's `ExecutorService` propagation does not cover the Eclipse `Job` worker pool).
. *EventAdmin instrumentation* with W3C trace-context propagation through event properties.
This is the largest "aha" effect because asynchronous data flows become coherent traces.
. *Raw SWT event firehose* - instrument `Widget.sendEvent` behind a strict event-type filter (deferred: `Paint`/`MouseMove` would flood without one).
. *Declarative Services* - instrument `@Component` activation and `@Reference` bindings.
. *Eclipse 4 `IEventBroker`* for richer topic-name spans.

Analysis and tooling::

. *jQAssistant integration* - compare static (jQAssistant) and dynamic (OTel) bundle dependency graphs to spot dead links and undeclared connections.
. *Bundle-graph tooling* - promote the ad-hoc `jq`/Graphviz edge-list recipe into a reusable helper script under `samples/`.
. *Neo4j / jQA import* - load the runtime `osgi.caller.bundle -> osgi.provider.bundle` edges as `(:Bundle)-[:USES]->(:Bundle)` for architecture queries (cycles, layer violations, undeclared uses), complementing the static structure jQAssistant already scans.

Considered and rejected::

* *Jaeger `peer.service` per bundle* - would only yield a star from the single `service.name` to pseudo-bundle nodes, not the real bundle-to-bundle topology (a per-bundle `service.name` is impossible with one agent Resource).
Use the data-derived Graphviz/Neo4j graph instead.
